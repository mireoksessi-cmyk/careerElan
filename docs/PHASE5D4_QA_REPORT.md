## 7. Public Resume Validation Summary — NOT TESTED

**Status: NOT TESTED**

**Reason (verbatim, per explicit instruction):** External PDF/DOCX bytes could not be obtained because of the execution environment limitations.

**What was actually attempted, and why it failed technically:**
1. **Bash shell network access:** `curl` to external hosts (including unrelated control domains, to rule out a target-specific block) consistently failed with connection reset — this sandbox's Bash tool has no outbound network access at all.
2. **Browser tool (`mcp__Claude_Browser__*`) navigation:** this tool does have real network access for page rendering, but:
   - Direct-file-download URLs (a `.pdf`/`.docx` link) trigger a native OS save dialog with no programmatic API to read the downloaded bytes; the tool's own guidance is not to retry such URLs.
   - `read_network_requests`'s response-body capture only works for the currently-loaded page's own in-page requests, not for file-download responses, and fails once navigation moves away from that page.

**Conclusion:** this is a structural limitation of the sandboxed execution environment, not a policy restriction or a skipped step. No external resume file's real bytes were run through the pipeline this round.

**What was explicitly NOT done, per instruction:** no external resume was manually reconstructed from visual inspection; no synthetic fixture was built to stand in for a real external resume and presented as external validation. Item 7 is reported at its true, measured value: **0 of a planned 20–30 real external resumes tested.**

**What DOES substitute, and does not:** §4's Resume Type Matrix and the 22-fixture gate referenced throughout this report cover a broad range of *synthetic* layouts (standard, two-column, sidebar, Canva-style, Word-native, tables, academic, metrics, multi-page, etc.), and Phase 5D.3's prior rounds did run a small number of real bench fixtures (`bench/resume-A..F`) through the pipeline. None of that substitutes for item 7's specific requirement — running genuinely external, license-clean, publicly sourced resume files (EUROPASS, Overleaf, university career-center samples, etc.) through the pipeline — which remains untested.

## 8. Layer Failure Analysis

**Bug #1 (real, newly discovered this round; root-caused only, NOT fixed per instruction):**

- **Location:** `lib/documentPreservation/resumeStructured/splitOrganizationLocation.ts`, `looksLikeLocation()`.
- **Defect:** the function's shape check requires `commaParts.length === 2`, so it only recognizes exactly-2-part comma locations (e.g. "Toronto, ON"). A legitimate 3-part location ("San Francisco, California, USA") fails this check.
- **Failure chain:** for a pipe-composite header line like `"Example University | San Francisco, California, USA"`, `parseInlineCompositeHeader`'s pipe-split path correctly finds the pipe boundary, calls `looksLikeLocation()` on the right-hand side, gets `false` (3 comma-parts ≠ 2), and falls through to `splitOrganizationLocation`'s trailing-comma fallback. That fallback operates on the **entire original string**, still containing the literal `|` character, and blindly splits on every comma — producing a corrupted result: `institutions = ["Example University | San Francisco"]` (pipe glued into the institution name) and `location = "California, USA"` (wrong, and missing "San Francisco").
- **Discovery context:** found while designing the negative-control suite's location-comma bucket. Confirmed real (not a test-authoring mistake) by manually tracing `parseInlineCompositeHeader` → `looksLikeLocation` → `splitOrganizationLocation`'s fallback against the actual source.
- **Handling this round:** the affected 3-part-location negative-control cases were removed from `academicNegativeControl.test.ts` rather than asserted as passing (which would have enshrined the bug as an expected contract). The bucket's own header comment documents the bug in full for whoever picks up the fix. No implementation file was touched.
- **Disposition:** deferred to a separate follow-up round, per this round's explicit "root-cause only, do not fix" instruction.

**No other real parser bugs were found this round.** Two other findings during test authoring (an initial flawed assertion about `"Bachelor of Science, Honours"` credential splitting, and an initial self-test phrase that tripped `looksLikeHeaderLine`'s 6-word cap) were both confirmed to be test-design mistakes on the QA author's part, not parser defects — both were corrected in the test files, not the implementation.

**Layer-by-layer status for everything else exercised this round:** all 56 regression test files (Phase 1 → Phase 5D, covering Lossless Semantic → Resume Structured → Professional ATS Assembly → HTML → PDF → DOCX → Parity) passed at 100%, 0 failures. No other layer showed a failure this round.

## 10. Production Readiness Verdict: **READY_WITH_LIMITATIONS**

**Justification:**

The Professional ATS Resume Engine's core pipeline (Lossless Semantic extraction → Resume Structured fields → Professional ATS Assembly → HTML/PDF/DOCX generation → cross-format Parity) is extensively and durably tested: 4,190 regression assertions across 56 files, 549 hand-authored academic-header-pattern assertions, and 234 negative-control assertions proving false positives are actively prevented (not just absent by chance — the self-test proves the harness itself can detect a real split). `tsc` and `npm run build` are clean, and no orphan processes leak from the test/build tooling. 30 of 52 audited resume types and 30 of 43 audited fields are fully SUPPORTED with concrete evidence; the engine's core English-language, single/multi-column, academic, metric-heavy, and mixed-content resume handling is solid.

It is **not** unconditionally READY for these concrete, disclosed reasons:

1. **One real, unfixed parser bug** (§8, Bug #1): 3-part comma-separated locations in pipe-composite headers corrupt the institution and location fields. Low-frequency shape, but a genuine correctness defect with no existing regression coverage protecting against it (it was found by this round's own new test-authoring, not caught by prior rounds).
2. **French/English-French/Korean academic-header parsing is explicitly unsupported**, not merely imperfect — the underlying keyword regexes are English-only by construction, and this is honestly disclosed in the codebase's own tests, not glossed over.
3. **A structural multi-column reading-order bug is UNFIXED and disclosed** (Feature Matrix #43): two-column PDFs can interleave unrelated sections' text; Phase 2 only defensively contains the damage, it does not correct it.
4. **item 7, external public-resume validation, is genuinely untested** (0/20–30) due to a real environment limitation, not a shortcut — meaning the engine's behavior against real, messily-formatted, non-synthetic external resumes remains unverified by this round.
5. A meaningful set of resume domains (technical, engineering, sales, PM, government, legal, entry-level, executive) have **no dedicated fixture or test at all** (NOT_TESTED, not NOT_SUPPORTED) — behavior there is unknown, not confirmed-bad, but also not confirmed-good.
6. Structurally, the engine has firm, disclosed, by-design non-goals (scanned/image-only PDFs, OCR, RTL, tables-as-tables, photos, charts, SmartArt, footnotes, password-protected/corrupted-file recovery beyond graceful failure) that a production rollout must message honestly to users rather than silently fail on.

None of these are hidden or estimated — every one is backed by a specific, re-verified test result or a direct code citation in this report. **Recommendation:** proceed to production for the SUPPORTED resume-type/feature surface with the Known Limitations Matrix surfaced honestly to users (e.g. an upload-guidance message covering unsupported formats/languages), fix Bug #1 in a dedicated follow-up round before it can cause a silent field-corruption in production, and treat item 7 as an open follow-up requirement — either by having a human supply real sample files directly, or via an environment with outbound file-download capability — before claiming real-world-resume validation coverage.
